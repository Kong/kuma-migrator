    mTLS and workload identity

    Moving a mesh from Mesh.mtls to MeshIdentity and MeshTrust before Kuma 3.0, and why kuma-migrator reports it instead of rewriting it.

    On 2.x a mesh gets mutual TLS from Mesh.spec.mtls: a CA backend (builtin, provided, or a Kong Mesh enterprise backend) issues every proxy a certificate. Kuma 2.12 added a second model, MeshIdentity + MeshTrust, which issues SPIFFE identities per workload. Kuma 3.0 keeps only the second one.

    What changed upstream

    Version Change
    2.12.0 MeshIdentity and MeshTrust introduced, with the Bundled and Spire providers (CHANGELOG)
    2.13 MeshTrust spec.origin removed from the API and CRD; the value moves to status.origin (UPGRADE)
    2.14.0 MeshIdentity Extension provider; Kong Mesh registers vault, acmpca, certmanager on it. See External PKI
    3.0 Mesh.mtls removed from the API. It issues nothing: a mesh whose only identity source is mtls serves and accepts plaintext, and MeshTLS and MeshTrafficPermission stop applying to its proxies (UPGRADE)
    3.0 The legacy mesh CA is no longer added to the MeshTrust bundle. Proxies still holding a legacy certificate are not trusted by MeshIdentity peers, with no rolling path back (UPGRADE)
    3.0 mtls.backends[].mode: PERMISSIVE no longer makes inbounds permissive. Only MeshTLS decides; without one, inbounds are Strict (UPGRADE)
    3.0 MeshTLS from[] removed; use rules[] (UPGRADE)
    3.0 MeshIdentity.spec.spiffeID is immutable; the trust domain is rendered once and recorded in status.trustDomain (UPGRADE)
    3.0 Kong Mesh vault, acm, certmanager CA backends removed (Kong Mesh upgrade notes)

    The upgrade does not delete the <mesh>.ca-builtin-cert-<backend> and <mesh>.ca-builtin-key-<backend> Secrets of a builtin backend. Delete them yourself once nothing needs the old CA (UPGRADE).

    The identity model is described in MADR-074 (SPIFFE compliance) and the MeshIdentity docs.

    MeshTLS is orthogonal

    MeshTLS is not an identity source. It sets the TLS version, cipher suites and the inbound mode (Strict / Permissive) of connections that already use mTLS. It needs an identity source underneath it: on 3.0 that is MeshIdentity. Moving to MeshIdentity does not require a MeshTLS policy, and adding one does not issue certificates (MeshTLS docs).

    spec.mtls on its own is not deprecated in 2.x and is safe to keep until the cutover.

    What kuma-migrator does

    Input --to-latest v2 --to-latest v3
    Mesh.spec.mtls Kept. Advisory: MeshIdentity migration required before 3.0 Removed from the output. Blocking warning: create a MeshIdentity (and MeshTrust) that selects every proxy before upgrading
    Enabled backend with mode: PERMISSIVE Kept. Warning to add a MeshTLS Permissive before 3.0 Companion MeshTLS <mesh>-tls-permissive with rules[].default.mode: Permissive
    builtin backend Advisory: the CA is in the <mesh>.ca-builtin-cert/key-<backend> Secrets; a Bundled MeshIdentity with autogenerate mints a new CA, or reuses the current one through spec.provider.bundled.ca.certificate/privateKey. Either way the CA is self-signed, so insecureAllowSelfSigned: true is required Same, in the blocking warning, plus: delete the ca-builtin Secrets yourself after the upgrade
    provided backend Advisory: reference the same conf.cert/conf.key material from spec.provider.bundled.ca; set insecureAllowSelfSigned: true if that CA is a self-signed root Same, in the blocking warning
    builtin or provided backend, any mesh Advisory: in a mesh that spans zones, create one MeshTrust per zone on the Global, or give every zone the same CA and trust domain (see Trust across zones) Same, in the blocking warning
    Kong Mesh vault / acmpca / certmanager backend Advisory names the MeshIdentity Extension provider; the CA stays in the external system, so no new CA is generated Same, in the blocking warning
    MeshTLS with from[] Converted to rules[] (Rules scenario) Same; a from[] source that is not kind: Mesh is warned, because rules[] widens it
    MeshTrust spec.origin Warning (removed in 2.13) Warning
    MeshMetric Prometheus tls.mode: ActiveMTLSBackend — Warning: on 3.0 remote scrapers need a client certificate the mesh trusts (UPGRADE)

    Code: v3_mesh.go, deprecation.go (warnMeshMtlsBackends).

    What it cannot do

    The tool never writes a MeshIdentity. The move is a CA cutover, not a field rename:

    • Trust domain. MeshIdentity renders a trust domain from a template (default {{ .Mesh }}.{{ .Zone }}.mesh.local). The zone name is runtime data, and on 3.0 the rendered value is fixed at creation.
    • SPIFFE paths. The default path is /ns/{{ .Namespace }}/sa/{{ .ServiceAccount }} on Kubernetes and /workload/{{ .Workload }} on Universal. Neither the service accounts nor the kuma.io/workload labels are in the Mesh manifest.
    • CA material. A builtin backend's CA lives in a control-plane Secret; a provided backend references Secrets or files; a Kong Mesh vault/acmpca/certmanager backend keeps it in the external system. For builtin and provided, a generated Bundled identity with autogenerate would mint a new CA, which is a new trust root, not a translation. The warning text is specific to each backend type, so builtin-only advice (new CA, ca-builtin Secrets) is not given for the others.
    • Zones. Whether the mesh spans zones, and each zone's generated CA bundle, are runtime data. See Trust across zones.
    • Rollout order. Which workloads move first, and when MeshTrafficPermission rules[] (which match SPIFFE IDs) replace from[], depends on the mesh. See Access control.

    Manual steps

    Run these on 2.14, mesh by mesh, before upgrading any control plane to 3.0.

    1. Decide the trust domain and path templates. The defaults work for most Kubernetes meshes. In a mesh that spans zones, decide now how zones trust each other (next section): the trust domain cannot be changed once the MeshIdentity exists on 3.0.
    2. Create a MeshIdentity (with meshTrustCreation: Enabled, or a hand-written MeshTrust) selecting a first group of proxies with spec.selector.dataplane.matchLabels. While Mesh.mtls is still enabled and a MeshTrust exists, 2.x adds the legacy mesh CA to the trust bundle, so MeshIdentity proxies keep trusting legacy peers (UPGRADE).
    3. Check DataplaneInsight mTLS.issuedBackend on the selected proxies, then widen the selector until it matches every proxy (matchLabels: {}). In a mesh that spans zones, create the per-zone MeshTrusts on the Global before you select proxies in a second zone.
    4. If the enabled backend used mode: PERMISSIVE, apply a MeshTLS with rules[].default.mode: Permissive (the v3 run generates it).
    5. Rewrite MeshTrafficPermission from[] to SPIFFE rules[] (see Access control).
    6. Give remote Prometheus scrapers of ActiveMTLSBackend endpoints a client certificate the mesh trusts, or set the mode to Disabled.
    7. Upgrade. Apply the v3 Mesh (without mtls). Delete the ca-builtin-* Secrets when no tooling needs them.

    A MeshIdentity for the whole mesh, using the default templates and a generated CA:

    apiVersion: kuma.io/v1alpha1
kind: MeshIdentity
metadata:
  name: identity
  namespace: kong-mesh-system
  labels:
    kuma.io/mesh: default
spec:
  selector:
    dataplane:
      matchLabels: {}
  spiffeID:
    trustDomain: "{{ .Mesh }}.{{ .Zone }}.mesh.local"
    path: "/ns/{{ .Namespace }}/sa/{{ .ServiceAccount }}"
  provider:
    type: Bundled
    bundled:
      meshTrustCreation: Enabled
      insecureAllowSelfSigned: true
      certificateParameters:
        expiry: 24h
      autogenerate:
        enabled: true

    insecureAllowSelfSigned: true is required with autogenerate, and with a ca that is a self-signed root. Without it the MeshIdentity fails validation (self-signed certificates are not allowed) and never becomes ready, and once Mesh.mtls is removed the mesh serves plaintext.

    This is the example from the Kong Mesh MeshIdentity docs. To keep your own CA, use bundled.ca.certificate / bundled.ca.privateKey (SecureDataSource) instead of autogenerate; for Vault, ACM Private CA or cert-manager see External PKI.

    Trust across zones

    On 2.x every zone used one mesh CA, generated on the Global and synced to the zones, so proxies in different zones trusted each other with no extra step. A Bundled MeshIdentity works differently: each zone generates its own CA, and the default trust domain {{ .Mesh }}.{{ .Zone }}.mesh.local differs per zone. The MeshTrust a zone creates for its CA is synced to the Global only. It never reaches the other zones.

    Open the diagram full size by selecting it.

    Resource Where you create it Synced to Needed for cross-zone mTLS
    MeshIdentity Global, once per mesh Every zone Yes: it is the identity source on 3.0. Each zone issues certificates from it
    MeshTrust created by a zone (meshTrustCreation: Enabled) The zone, automatically The Global only, read-only Covers that zone's own proxies only
    MeshTrust per zone, origin global Global, one per zone, with that zone's CA bundle and trust domain Every zone Yes, unless every zone shares one CA and trust domain

    Two ways to make zones trust each other. Pick one before proxies in a second zone get an identity, because the trust domain cannot be changed on 3.0 once the MeshIdentity exists:

    1. One MeshTrust per zone, created on the Global. After the MeshIdentity is ready in a zone, read the CA bundle and trust domain from that zone's auto-created MeshTrust (the read-only copy on the Global shows them) and create a MeshTrust on the Global with the same caBundles and trustDomain. Repeat for each zone. Each zone keeps its own CA.
    2. One CA and one trust domain for every zone. Set spec.provider.bundled.ca to the same CA in every zone and a spec.spiffeID.trustDomain without {{ .Zone }}. The zones' auto-created MeshTrusts then hold the same CA, and no extra MeshTrust is needed. This is closest to the 2.x model, and it keeps one trust root for the whole mesh.

    A per-zone MeshTrust on the Global:

    apiVersion: kuma.io/v1alpha1
kind: MeshTrust
metadata:
  name: trust-east
  namespace: kong-mesh-system
  labels:
    kuma.io/mesh: default
spec:
  trustDomain: default.east.mesh.local
  caBundles:
    - type: Pem
      pem:
        value: |-
          -----BEGIN CERTIFICATE-----
          … the CA bundle of zone east's auto-created MeshTrust …
          -----END CERTIFICATE-----

    The Kuma docs describe the per-zone trust domains in MeshTrust, Multizone. kuma-migrator cannot write these MeshTrusts: the CA bundles exist only once each zone has generated its CA. Its v2 advisory and v3 blocking warning name both options.

    Example

    Input:

    apiVersion: kuma.io/v1alpha1
kind: Mesh
metadata:
  name: default
spec:
  meshServices:
    mode: Exclusive
  networking:
    outbound:
      passthrough: false
  mtls:
    enabledBackend: ca-1
    backends:
      - name: ca-1
        type: builtin
        mode: PERMISSIVE
        dpCert:
          rotation:
            expiration: 1d

    --to-latest v2 keeps mtls and extracts the passthrough setting:

    # mesh/Mesh-default.yaml
apiVersion: kuma.io/v1alpha1
kind: Mesh
metadata:
  name: default
spec:
  meshServices:
    mode: Exclusive
  mtls:
    backends:
    - dpCert:
        rotation:
          expiration: 1d
      mode: PERMISSIVE
      name: ca-1
      type: builtin
    enabledBackend: ca-1

    --to-latest v3 drops mtls and adds the MeshTLS that keeps inbounds permissive (the MeshPassthrough None is generated on both targets):

    # mesh/Mesh-default.yaml
apiVersion: kuma.io/v1alpha1
kind: Mesh
metadata:
  name: default
spec:
  meshServices:
    mode: Exclusive

    # zero-trust/MeshTLS-kuma-system-default-tls-permissive.yaml
apiVersion: kuma.io/v1alpha1
kind: MeshTLS
metadata:
  labels:
    kuma.io/mesh: default
  name: default-tls-permissive
  namespace: kuma-system
spec:
  rules:
  - default:
      mode: Permissive
  targetRef:
    kind: Mesh

    The v3 blocking warning (shortened):

    ⚠  Mesh "default": spec.mtls is REMOVED in 3.0 and has been dropped from the Mesh output.
   BLOCKING: before upgrading, create a MeshIdentity (and MeshTrust) that selects every proxy in
   this mesh, unless one already does. On 3.0 spec.mtls issues no certificates: a mesh whose only
   identity source is spec.mtls serves and accepts plaintext, and MeshTLS and
   MeshTrafficPermission stop applying to its proxies. …

    v3: Apply the v3 Mesh only after the MeshIdentity covers every proxy. Applying it earlier on a 2.x control plane turns mTLS off for the mesh.
