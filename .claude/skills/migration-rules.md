# Kuma Migrator — Migration Rules

Authoritative reference for transformation logic. Consult before writing or modifying
any scenario transform, detection logic, or deprecation scanner.

---

## 1. Scenario Overview

| Scenario | Constant | Trigger | Output |
|---|---|---|---|
| Legacy | `ScenarioLegacy` | Top-level `sources`/`destinations`/`selectors` or non-`Mesh*` `type` | `targetRef`/`to`/`from`/`rules`/`default` — see §6 |
| Subset | `ScenarioSubset` | `Mesh*` kind + `MeshSubset` with service-identity tags | `Dataplane`/`MeshService` targetRefs |
| Passthrough | `ScenarioPassthrough` | `Mesh*` kind + no service-identity tags + no `from[]` | pass through unchanged |
| Rules | `ScenarioRules` | `Mesh*` kind + `from[]` + no service-identity tags | `from[]` → `rules[]` |
| Mesh | `ScenarioMesh` | `kind: Mesh` + embedded observability/passthrough OR missing `meshServices.mode: Exclusive` | standalone companion CRDs + cleaned Mesh |
| ExternalService | `ScenarioExternalService` | `kind: ExternalService` | `kind: MeshExternalService` |
| Gateway | `ScenarioGateway` | `kind: MeshGateway` | `kind: Gateway` (gateway.networking.k8s.io) |
| GatewayInstance | `ScenarioGatewayInstance` | `kind: MeshGatewayInstance` | `GatewayClass` + `MeshGatewayConfig` |
| HTTPRoute | `ScenarioHTTPRoute` | `kind: MeshHTTPRoute` | `kind: HTTPRoute` |
| TCPRoute | `ScenarioTCPRoute` | `kind: MeshTCPRoute` | `kind: TCPRoute` |
| GatewayRoute | `ScenarioGatewayRoute` | `kind: MeshGatewayRoute` | `HTTPRoute`/`TCPRoute` |
| OPAPolicy | `ScenarioOPAPolicy` | `kind: OPAPolicy` (Kong Mesh) | `kind: MeshOPA` |

## 2. Detection Order

`DetectScenario` in `detect.go` must evaluate in this order (first match wins):

1. **Passthrough** — `kind` is a Gateway API native kind (`Gateway`, `HTTPRoute`, `TCPRoute`, etc.) → `ScenarioPassthrough`
2. **ExternalService** — `kind: ExternalService` → `ScenarioExternalService`
3. **Mesh** — `kind: Mesh` + `meshNeedsMigration()` returns true → `ScenarioMesh`; otherwise `ScenarioPassthrough`
4. **Gateway/Instance/Routes** — `kind: MeshGateway/MeshGatewayInstance/MeshHTTPRoute/MeshTCPRoute/MeshGatewayRoute`
5. **OPAPolicy** — `kind: OPAPolicy` → `ScenarioOPAPolicy`
6. **Recognised non-policy** — `kind` in `recognisedNonPolicyKinds` (`ContainerPatch`) → `ScenarioPassthrough`
7. **Legacy** — top-level `sources` or `destinations` key present, OR `type` is in `knownLegacyTypes` → `ScenarioLegacy`
8. **Mesh*-style policies** — has `apiVersion: kuma.io/v1alpha1` + `Mesh*` kind:
   - If any `targetRef` has service-identity tags → `ScenarioSubset`
   - Else if `from[]` is present → `ScenarioRules`
   - Else → `ScenarioPassthrough`

**Service-identity tags** (presence of either triggers Subset detection):
- `kuma.io/service`
- `k8s.kuma.io/service-name`

## 3. ScenarioLegacy — Tag Value → MeshService Name Conversion

### 3.1 `kuma.io/service` tag (Kubernetes format)

Auto-generated by Kuma CP as `<service>_<namespace>_svc_<port>`:

```
kuma.io/service: backend_demo_svc_3001
  → name:      backend
  → namespace: demo
  → port:      3001
```

**Parsing algorithm:**
1. Split on `_svc_` → left part is `<name>_<namespace>`, right part is port
2. Split left part on the **last** `_` to separate namespace (names may contain `_`)
3. `'*'` → `kind: Mesh` (wildcard, not a service reference)

**Universal mode:** `kuma.io/service` values are free-form (not `_ns_svc_port` encoded).
Detect Universal mode by the absence of `k8s.kuma.io/*` labels. Use the raw tag value
as the `MeshService` name.

### 3.2 `k8s.kuma.io/service-name` tag

Directly holds the Kubernetes Service name:

```
tags:
  k8s.kuma.io/service-name: redis
  k8s.kuma.io/namespace: demo   # optional

→ kind: MeshService, name: redis, namespace: demo
```

### 3.3 Non-service tags → `labels`

`MeshSubset` entries with **both** service-identity and other tags: output uses
`kind: MeshService` with `labels` for the non-service refinements:

```yaml
# Input
kind: MeshSubset
tags:
  kuma.io/service: backend_demo_svc_3001
  version: v2

# Output
kind: MeshService
labels:
  kuma.io/display-name: backend
  k8s.kuma.io/namespace: demo
  version: v2
```

If **only** non-service tags: keep `MeshSubset` unchanged (workload selector, not service selector).

## 4. targetRef Mapping Tables

### 4.1 `spec.targetRef` (top-level — "who this policy applies to")

Since Kuma 2.10 `spec.targetRef` takes `kind: Dataplane` (with `labels`, optionally
`sectionName`) in place of the deprecated `MeshSubset` (UPGRADE.md "New kind Dataplane for
targetRef in policies"); in 2.13+ only `Mesh` and `Dataplane` are valid. `MeshService` is
**not** valid at the top level.

**A generated top-level `Dataplane` always uses `labels`, never `name`/`namespace`, on v2
and v3 alike.** `Dataplane{name}` selects one Dataplane by its own name — the pod name on
Kubernetes (`web-6d4f8c-xk2pq`) — never the service name decoded from a tag, so it would
match nothing. On Kubernetes a Dataplane's labels are its pod's labels (merged by the pod
converter) plus the CP-set `k8s.kuma.io/namespace`, `kuma.io/zone`, `kuma.io/mesh`,
`kuma.io/origin`, `kuma.io/env`. `kuma.io/display-name` on a Dataplane is the proxy's own
name, so it is never used to select by service. `app: <svc>` is a best guess at the pod label
and always warned (`buildLabels`); on Universal (no namespace in the tag) the warning also
says a Dataplane carries only its own `labels` field.

| Input | Output |
|---|---|
| `kind: Mesh` | `kind: Mesh` (unchanged) |
| `kind: MeshSubset, tags: {kuma.io/service: '*'}` | `kind: Mesh` |
| `kind: MeshSubset, tags: {kuma.io/service: svc_ns_svc_port}` | `kind: Dataplane, labels: {app: svc, k8s.kuma.io/namespace: ns}` (warned) |
| `kind: MeshSubset, tags: {k8s.kuma.io/service-name: svc, k8s.kuma.io/namespace: ns}` | `kind: Dataplane, labels: {app: svc, k8s.kuma.io/namespace: ns}` (warned) |
| `kind: MeshSubset, tags: {kuma.io/service: X_ns_svc_p, version: v2}` | `kind: Dataplane, labels: {app: X, k8s.kuma.io/namespace: ns, version: v2}` |
| `kind: MeshSubset, tags: {non-service tags only}` | `kind: Dataplane, labels: {<tags>}` |
| `kind: MeshService, name: svc_ns_svc_port[, sectionName: s]` (partially migrated) | `kind: Dataplane, labels: {app: svc, k8s.kuma.io/namespace: ns}[, sectionName: s]` |
| `kind: Dataplane, name/labels: {...}` | unchanged |

From old `sources[]`/`destinations[]`/`selectors[]` (ScenarioLegacy) and `OPAPolicy` selectors:

| Old match | New `spec.targetRef` |
|---|---|
| `kuma.io/service: '*'` | `kind: Mesh` |
| `kuma.io/service: svc_ns_svc_port` | `kind: Dataplane, labels: {app: svc, k8s.kuma.io/namespace: ns}` |
| service tag + other tags | `kind: Dataplane, labels: {app: svc, k8s.kuma.io/namespace: ns, <other tags>}` |

**Reserved tags are not copied into a labels selector** (`selectorLabelsFromTags` in
`convert.go`, top level and `to[]`/`from[]`). Tags in the `kuma.io` domain or a subdomain
(`k8s.kuma.io/…`) are dropped, with a warning naming them, unless they are also labels on
Dataplanes/MeshServices: `kuma.io/zone`, `kuma.io/env`, `kuma.io/mesh`, `kuma.io/origin`,
`k8s.kuma.io/namespace` (kuma `pkg/core/resources/labels/registry.go`). Example:
`{kuma.io/service: backend_demo_svc_3001, kuma.io/protocol: http}` →
`labels: {app: backend, k8s.kuma.io/namespace: demo}` — no Dataplane has a `kuma.io/protocol`
label (`kuma.io/instance`, `k8s.kuma.io/service-port` likewise). Tags kept as `MeshSubset`
`tags` (not labels) are untouched.

### 4.2 `to[].targetRef` (outbound — "where traffic goes")

| Input | Output |
|---|---|
| `kind: Mesh` | `kind: Mesh` (unchanged) |
| `kind: MeshSubset, tags: {kuma.io/service: svc_ns_svc_port}` | `kind: MeshService, name: svc, namespace: ns` ¹ |
| `kind: MeshSubset, tags: {kuma.io/service: ..., kuma.io/zone: east}` | `kind: MeshService, labels: {kuma.io/display-name: svc, k8s.kuma.io/namespace: ns, kuma.io/zone: east}` |
| Old `destinations: [{match: {kuma.io/service: svc_ns_svc_port}}]` | `kind: MeshService, name: svc, namespace: ns` ¹ |
| Old `destinations: [{match: {kuma.io/service: '*'}}]` | `kind: Mesh` |

¹ Use `name/namespace` when the policy namespace matches the target's namespace.
  Use `labels` (`kuma.io/display-name` + `k8s.kuma.io/namespace`) when the policy is in
  a system namespace or on Global CP (name/namespace would be ambiguous across zones).

### 4.3 `from[].targetRef` (inbound — "who sends traffic")

Same rules as `to[].targetRef`, including the `name/namespace` vs `labels` scoping rule,
**except `MeshTrafficPermission` and `MeshFaultInjection` under v2**: UPGRADE.md 2.7
("Deprecation of 'from[].targetRef.kind: MeshService'") deprecates `MeshService` in their
`from[]` and gives `kind: MeshSubset, tags: {kuma.io/service: <value>}` instead. So
(`fromSubsetRefV2`, `fromRefForTarget` in `convert.go`):

| Input (MTP/MFI `from[]`, v2) | Output |
|---|---|
| Legacy source `{kuma.io/service: '*'}` or empty | `kind: Mesh` |
| Legacy source `{kuma.io/service: web_demo_svc_80, version: v2}` | `kind: MeshSubset, tags: {kuma.io/service: web_demo_svc_80, version: v2}` (tag value kept verbatim — it is the Dataplane's own inbound tag) |
| `kind: MeshSubset, tags: {...}` (Subset scenario) | unchanged |
| `kind: MeshService, name: svc_ns_svc_port` (partially migrated) | `kind: MeshSubset, tags: {kuma.io/service: svc_ns_svc_port}` |

Under v3 `from[]` is removed from both kinds; see §18.

### 4.4 `name/namespace` vs `labels` scoping rule

Applies to `to[]`/`from[]` `MeshService` refs on v2. The top level is always labels (§4.1).

| Policy location | Use |
|---|---|
| Same namespace as target resource | `name` + `namespace` |
| System namespace (`kuma-system`, `kong-mesh-system`) | `labels` |
| Global CP | `labels` (a MeshService with the same name can exist in multiple zones) |

Use `kuma.io/display-name` (not `k8s.kuma.io/service-name`) for cross-namespace label
selection. The CP sets `kuma.io/display-name` on every auto-generated MeshService.

**Kuma 3.0: `labels` only.** Policies select `Dataplane`, `MeshService`, `MeshExternalService`,
`MeshMultiZoneService` and `MeshHTTPRoute` (in `spec.targetRef`, `spec.to[].targetRef` and route
`backendRefs`) by `labels` only; `name`/`namespace`/`mesh` are gone (`sectionName` stays). Under
`--to-latest v3` the converter always emits labels (`ConvertTargetRefForTarget`): `name` →
`kuma.io/display-name`, `namespace` → `k8s.kuma.io/namespace`, `mesh` → `kuma.io/mesh`. A zone-origin
policy also pins `kuma.io/zone`. `Dataplane{name}` cannot be converted (a Dataplane name is not a
label); the document is reported as rejected (§4.5). The table above applies to v2 output only.

**Kuma 3.0 producer role needs `kuma.io/zone`.** `ComputePolicyRole` (kuma
`pkg/core/resources/labels/compute.go`) counts a `to[]` item as producer only when its kind is
`MeshService`/`MeshHTTPRoute` and its labels are **exactly three**: `kuma.io/display-name`,
`k8s.kuma.io/namespace` == the policy's namespace, `kuma.io/zone` == the policy's own zone
(empty zone → never producer, so producers exist only on Zone CPs). All items producer →
`producer`; none → `consumer`; a mix is rejected. The 2-label rewrite of `{name, namespace}` is
therefore a consumer policy. `pinProducerZoneForV3` (`v3_policy.go`) runs after the rewrite:
for a producer policy (`kuma.io/policy-role: producer`, or no role label + app namespace + every
`to[]` item a `MeshService`/`MeshHTTPRoute` of that namespace) it adds `kuma.io/zone` from the
policy's own `kuma.io/zone` label; when absent it warns naming each selector that needs
`kuma.io/zone: <zone-name>` (no zone name is available elsewhere: `ContextMeta` has none).
Extra labels on a producer selector are warned (they make it a consumer).

### 4.5 Documents the target rejects (`RejectedByTargetError`)

`TransformDocumentWithOptions` returns `*RejectedByTargetError` (`rejected.go`) **together
with** the converted docs and warnings when, under v3, an output document is one 3.0 rejects
as written (`v3RejectionReasons`): `spec.from` on `MeshTrafficPermission`/`MeshFaultInjection`;
a top-level kind other than `Mesh`/`Dataplane`; `name`/`namespace` on a `Dataplane`,
`MeshService`, `MeshExternalService`, `MeshMultiZoneService` or `MeshHTTPRoute` ref; a `to[]`
kind the policy's 3.0 validator rejects (`warnV3ToTargetRefKinds`). `Rejected[]` lists the
indices into the returned docs. The pipeline routes those to `_manual/`, never to the apply
tree. Never set under v2. Separately, any generated document with an empty kind/type or name
is a hard error (`unnamedOutputError`), never a silent `other/unknown.yaml`.

## 5. Policy Type Renaming (ScenarioLegacy)

| Old `type` | New `kind` |
|---|---|
| `Timeout` | `MeshTimeout` |
| `CircuitBreaker` | `MeshCircuitBreaker` |
| `Retry` | `MeshRetry` |
| `TrafficPermission` | `MeshTrafficPermission` |
| `FaultInjection` | `MeshFaultInjection` |
| `RateLimit` | `MeshRateLimit` |
| `HealthCheck` | `MeshHealthCheck` |
| `TrafficLog` | `MeshAccessLog` |
| `TrafficTrace` | `MeshTrace` |
| `TrafficRoute` | **error** — requires manual migration to `MeshHTTPRoute`/`MeshTCPRoute` |
| `ProxyTemplate` | `MeshProxyPatch` |
| `VirtualOutbound` | **error** — requires manual migration (`HostnameGenerator` + `MeshHTTPRoute`/`MeshTCPRoute`) |

These are the 12 legacy policy resources Kuma 3.0 removes from the resource
registry. `ExternalService` (→ `MeshExternalService`) is removed in 3.0 as well but
has its own scenario. **`ContainerPatch` is not in this set**: it is a
Kubernetes-only JSON-patch resource for the injected sidecar/init containers, it
has no `targetRef` successor, and it is still served in 3.0 — pass it through
unchanged (`recognisedNonPolicyKinds` in `detect.go`).

## 6. Legacy Policy Shape (`legacyShapes` in `transform.go`)

The legacy selector fields do not map onto the new API the same way for every kind.
Getting this wrong produces a policy attached to the wrong proxy.

| Shape | Kinds | Mapping |
|---|---|---|
| **outbound** | `Timeout`, `CircuitBreaker`, `Retry`, `HealthCheck`, `TrafficLog` | `sources` → `spec.targetRef`; `destinations` → `to[].targetRef` |
| **inbound** (inverted) | `TrafficPermission`, `FaultInjection`, `RateLimit` | `destinations` → `spec.targetRef`; `sources` → `from[].targetRef` |
| **selector** | `TrafficTrace`, `ProxyTemplate` | `selectors` → `spec.targetRef`; conf → `spec.default` (successors have no `to[]`/`from[]`) |

Notes:

- `FaultInjection` and `RateLimit` are enforced by the **destination's** sidecar,
  exactly like `TrafficPermission`. Treating them as outbound targets the client.
- `RateLimit` → `MeshRateLimit` emits **`rules[]`, not `from[]`**: local rate
  limiting is client-agnostic (`from[]` accepts only `kind: Mesh`, and 3.0 removes
  `from[]` with `rules[]` as the documented mechanical replacement). Any specific
  `sources` selector is lost — warn loudly, it is a scope widening.
- `TrafficTrace` and `ProxyTemplate` scope with `selectors[]`, **not**
  `sources`/`destinations`. `UniversalPolicy.Selectors` must be populated or both
  the scope and the conf are dropped and the output is an empty shell policy.
- An empty `destinations` list means "all destinations"; substitute a wildcard
  selector so the conf still has a `to[]` entry to live in.

## 6b. Legacy `conf` → new `default` (`legacyconf.go`)

**A legacy `conf` body is never structurally compatible with the new `default`
section.** Copying it verbatim yields a document that applies cleanly and silently
does nothing. Every converter is written as an explicit list of moves, and
`confMapper.unmapped()` reports any input leaf no move consumed.

| Legacy | New | Notable changes |
|---|---|---|
| `Timeout` | `MeshTimeout` | `connectTimeout`→`connectionTimeout`; `tcp.idleTimeout`→`idleTimeout`; **no `grpc` section** (folds into `http`); no `http.idleTimeout` |
| `CircuitBreaker` | `MeshCircuitBreaker` | `thresholds.*`→`connectionLimits.*`; everything else under `outlierDetection`; `detectors.totalErrors`→`totalFailures`, `gatewayErrors`→`gatewayFailures`, `localErrors`→`localOriginFailures`, `standardDeviation`→`successRate` (`factor`→`standardDeviationFactor`), `failure`→`failurePercentage` |
| `Retry` | `MeshRetry` | `tcp.maxConnectAttempts`→**`maxConnectAttempt`** (singular); `retryOn` enum snake_case→CamelCase; `retriableMethods`→`retryOn: [HttpMethodGet, …]`; grpc `cancelled`→**`Canceled`**; `retriableStatusCodes` and `retryOn: retriable_status_codes`/`retriable_headers` have **no equivalent** (dropped, warned) |
| `HealthCheck` | `MeshHealthCheck` | `http.requestHeadersToAdd: [{header:{key,value},append}]` → `{add:[{name,value}], set:[…]}` (`append` unset defaults to **true** → `add`); `tcp.send`/`receive` stay base64 |
| `FaultInjection` | `MeshFaultInjection` | the single conf becomes a one-element `default.http[]` list |
| `RateLimit` | `MeshRateLimit` | `http.{requests,interval}`→`local.http.requestRate.{num,interval}`; `onRateLimit.headers[{key,value,append}]`→`{add,set}` with `name` |
| `TrafficLog` | `MeshAccessLog` | `conf.backend` is a **name reference** into `Mesh.spec.logging.backends` — resolved via `MeshBackendIndex`, inlined as `default.backends[]` |
| `TrafficTrace` | `MeshTrace` | same indirection against `Mesh.spec.tracing.backends`; the backend's `sampling` becomes `default.sampling.overall` |
| `ProxyTemplate` | `MeshProxyPatch` | `modifications`→`appendModifications`; operation `add`/`remove`/`patch`→`Add`/`Remove`/`Patch`, except `httpFilter`/`networkFilter`/`virtualHost` where `Add` does not exist (→ `AddLast`, warned); `imports` and `resources` have **no equivalent** |
| `TrafficPermission` | `MeshTrafficPermission` | no conf; synthesise `{action: Allow}` per `from[]` entry |

Percentages: whole numbers stay numeric, fractions become strings — the new
schemas type these as `anyOf: [integer, string]`.

**Cross-document context.** `TrafficLog`/`TrafficTrace` need the `Mesh` resource,
which the policy document does not contain. `runMigration` runs
`BuildMeshBackendIndex(inputDir)` as a pre-pass and threads it through
`TransformOptions`. When the `Mesh` is not in the input set the conversion emits a
warning naming the backend to write by hand rather than an empty policy.

## 7. Splitting for Multiple Sources (ScenarioLegacy)

When `sources[]` has multiple specific (non-wildcard) services, emit **one policy per
source** because `spec.targetRef` accepts only a single reference:

```yaml
# Input: one policy, two sources
sources:
  - match: {kuma.io/service: frontend_demo_svc_8080}
  - match: {kuma.io/service: backend_demo_svc_3001}
destinations:
  - match: {kuma.io/service: redis_demo_svc_6379}

# Output: two policies
---
spec:
  targetRef: {kind: Dataplane, name: frontend, namespace: demo}
  to: [{targetRef: {kind: MeshService, name: redis, namespace: demo}, default: <conf>}]
---
spec:
  targetRef: {kind: Dataplane, name: backend, namespace: demo}
  to: [{targetRef: {kind: MeshService, name: redis, namespace: demo}, default: <conf>}]
```

Name split policies `<original>-0`, `<original>-1`, etc.

## 8. ScenarioRules — `from[]` → `rules[]` (Kuma 2.10+)

### 8.1 Supported kinds (ScenarioRules applies)

The `rules:` block replaced `from:` for inbound traffic in Kuma 2.10 for these five kinds:

| Kind | Notes |
|---|---|
| `MeshAccessLog` | |
| `MeshCircuitBreaker` | |
| `MeshRateLimit` | |
| `MeshTimeout` | |
| `MeshTls` | |

These are the **only** kinds in `rulesAPIMigrationKinds`. Any new kind that gains `rules:` support must be added to that map explicitly.

### 8.2 Excluded kinds — `from:` stays permanent

These two kinds explicitly **do not** support the Rules API and must **never** be added to `rulesAPIMigrationKinds`. Their `from:` block is the intended, permanent API — not a deprecation:

| Kind | Reason |
|---|---|
| `MeshTrafficPermission` | Cannot match subsets of incoming traffic; `from:` is the only inbound mechanism |
| `MeshFaultInjection` | Same — inbound-only policy; no Rules API equivalent |

When these kinds have a `from:` block they fall through to `ScenarioPassthrough` (pass through unchanged).

**Superseded for 3.0.** Both kinds now have a `rules[]` API and 3.0 removes `from` from them
(MTP: "policy must define rules"). They are still excluded from `rulesAPIMigrationKinds` because the
rewrite is not mechanical for MTP: `rules[].default.{allow,deny,allowWithShadowDeny}[]` matches SPIFFE
IDs, which need a `MeshIdentity` and trust domain the manifest does not carry. Under v3:
- legacy `TrafficPermission` conversion errors;
- legacy `FaultInjection` and hand-written `MeshFaultInjection` convert to `rules[]` (no `matches`)
  only when every source is `kind: Mesh` / `kuma.io/service: '*'`; anything else errors or warns;
- a passthrough MTP with `from[]` is warned as rejected by 3.0.

### 8.3 Transformation

```yaml
# Input (from[]-based, deprecated in 2.10)
spec:
  targetRef:
    kind: Dataplane
    labels:
      app: backend
  from:
    - targetRef:
        kind: Mesh
      default:
        connectTimeout: 5s

# Output (rules-based)
spec:
  targetRef:
    kind: Dataplane
    labels:
      app: backend
  rules:
    - default:
        connectTimeout: 5s
```

**Warning:** If `from[]` has multiple entries with different `targetRef` values (source-specific
rules), each entry collapses into a `rules[]` entry without source discrimination. Emit a
warning: the source-specific targeting is lost and all inbound traffic will be affected.

`to[]` is preserved unchanged alongside `rules[]`.

## 9. ScenarioMesh — Mesh CRD Transformation

`meshNeedsMigration()` returns `true` when any of these conditions hold:
- `spec.metrics` is set
- `spec.tracing` is set
- `spec.logging` is set
- `spec.networking.outbound.passthrough` is set
- `spec.meshServices.mode` is not `"Exclusive"`

**Extracted companion CRDs:**

| Mesh section | Output kind |
|---|---|
| `spec.metrics` (prometheus) | `MeshMetric` from `enabledBackend` only (no `enabledBackend` → none: metrics were off) |
| `spec.tracing` (zipkin/datadog) | **none** — removed with a warning; backends only declare destinations on 2.x, a `TrafficTrace` activates them and its conversion inlines the backend |
| `spec.logging` (file/tcp) | **none** — same, via `TrafficLog` |
| `spec.networking.outbound.passthrough: false` | `MeshPassthrough` with `passthroughMode: None` |

A mesh-wide `MeshTrace`/`MeshAccessLog` would turn tracing/logging on for every proxy. The
warning uses `TransformOptions.LegacyObservability` (pre-pass index of TrafficLog/TrafficTrace
`conf.backend` per mesh) to list referenced vs inactive backends.

Companions keep the Mesh's format (Universal → `type`/`name`/`mesh`). On Kubernetes they go in
the system namespace (`resolveSystemNamespace`): config `systemNamespace` → pre-pass inference
(`namespace: kong-mesh-system` seen → that; `namespace: kuma-system` seen → that; Kong Mesh-only
kind → `kong-mesh-system`) → the document's own namespace → `kuma-system`. Same rule for the
MES converted from `ExternalService` and the v3 `MeshOpenTelemetryBackend`.

**Always injected:**
- `spec.meshServices.mode: Exclusive` is set on every processed Mesh CRD (with a warning
  to verify all policies and workloads are migrated first).

Companion CRD naming: `<meshName>-metrics`, `<meshName>-passthrough`, `<meshName>-tls-permissive` (v3). Validate names against RFC 1035/1123 and emit a warning if
the mesh name would produce an invalid name.

Structural mapping:

| ExternalService field | MeshExternalService field |
|---|---|
| `networking.address` (host:port) | `spec.match.port.value` + `spec.match.hostname` |

## 11. ScenarioOPAPolicy → MeshOPA (Kong Mesh)

```yaml
# Input
spec:
  conf:
    policies:
      - inlineString: "<rego>"
    agentConfig:
      inlineString: "<config>"   # optional

# Output
spec:
  default:
    appendPolicies:
      - rego:
          inlineString: "<rego>"
    agentConfig:
      inlineString: "<config>"   # if present
```

Each `policies[]` entry and `agentConfig` copies whichever of `inlineString` / `inline` (base64) /
`secret` it has (`convertLegacyOPADataSource`); the 2.x MeshOPA accepts all three. An entry
with none of them is left out with a "NOT migrated" warning — never an empty `rego: {}`.

`targetRef` is preserved unchanged. `MeshOPA` produces static config; dynamic config
via `MeshOPAPolicy` requires manual setup.

## 14. `meshServices.mode` on the `Mesh` resource

Four modes, from `Mesh_MeshServices_Mode` in `kuma/api/mesh/v1alpha1/mesh.proto`:

| Mode | Behaviour |
|---|---|
| `Disabled` (0) | No `MeshService` generation. **This is what a nil `meshServices` block resolves to on 2.x** (`MeshServicesMode()` in `api/mesh/v1alpha1/mesh_helpers.go`). |
| `Everywhere` (1) | Both `kuma.io/service` and `MeshService` generate Envoy clusters/CLAs — roughly twice the resources. |
| `ReachableBackends` (2) | `MeshService`s are generated but only materialised into a proxy's config where that `Dataplane` lists them in `transparentProxying.reachableBackends`. **`kuma.io/service` stays fully active** — this is the gradual, consumer-by-consumer on-ramp. |
| `Exclusive` (3) | **Only** `MeshService`/`MeshExternalService`/`MeshMultiZoneService`. Legacy tag matching disabled. |

Only `Exclusive` turns `kuma.io/service` off.

`kuma-migrator` always sets `spec.meshServices.mode: Exclusive` on every Mesh CRD it
processes. This is required for MeshService-based policies to take effect.

**Before enabling Exclusive mode**, confirm all policies and workload env-var addresses
in the mesh have been migrated.

**Kuma 3.0 (released notes):** `meshServices` no longer has any effect; unified naming is
unconditional. The field **stays in the schema as deprecated** so stored values keep syncing to
zones over KDS: a 2.x zone reads a missing field as `Disabled` and deletes every generated
`MeshService`. So `Exclusive` must be set on every mesh **before** the Global CP upgrade, and 3.0
rejects writes with any other mode. Drop the field once every zone runs 3.0. The migrator keeps
injecting `Exclusive` on both targets and says this under v3.
Related 3.0 removals: `Dataplane.spec.networking.transparentProxying.reachableServices`
and the `kuma.io/transparent-proxying-reachable-services` annotation, both replaced
by `reachableBackends` / `kuma.io/reachable-backends`.

## 15. RFC 1035 / RFC 1123 Name Validation (Kuma 2.10+)

**RFC 1035 kinds** (stricter — lowercase, alphabetic start, max 63 chars; a hard error on 3.0):
`Mesh`, `Zone`, `MeshService`, `MeshExternalService`, `MeshMultiZoneService`

**RFC 1123 kinds** (all others — alphanumeric start allowed):
Everything else

`ValidateResourceName(name, kind)` in `validate.go` returns a warning string if the
name violates the applicable standard. Call it:
1. When reading input resource names in all `TransformXxx` functions
2. When generating output resource names (e.g. `<meshName>-metrics`)

## 16. Address Mapping Scanner

Scans `Deployment`, `StatefulSet`, `DaemonJob` env var values for patterns matching
`<svc>_<ns>_svc_<port>.mesh` (legacy kuma.io/service encoded addresses).

Produces an `AddressMapping` entry with:
- `OldToken` — the encoded service token (e.g. `backend_demo_svc_3001`)
- `ExplicitPort` — the `.mesh` suffix and any explicit port
- `NewK8sAddress()` — `backend.demo.svc.cluster.local:3001`
- `NewMeshAddress()` — `backend.demo.svc.mesh.<zone>`

Deduplicated by `OldToken` in the final report.

## 18. Kuma / Kong Mesh 3.0 (`--to-latest v3`)

The full per-entry coverage of the 3.0.0 upgrade notes (which files handle what, and the
judgement calls) is in `CLAUDE.md`, section "Kuma / Kong Mesh 3.0 GA coverage". Rules to keep in
mind when writing new transform logic:

- Never emit a field 3.0 removed: 3.0 rejects unknown fields (`spec.from: unknown field`).
- Never copy control-plane-owned labels (`kuma.io/origin`, `zone`, `display-name`, `policy-role`,
  `k8s.kuma.io/namespace`, …) onto a resource's own labels; 3.0 rejects a value that differs from
  the computed one. `stripControlPlaneLabels` removes them under v3. Selector labels are untouched.
- Write `kuma.io/mesh` as a label, never an annotation.
- Anything the tool cannot convert under v3 goes to the `_manual/` subtree, not the apply tree.
