# Open questions settled against real control planes

Kong Mesh 2.14.7 and 3.0.1, Kubernetes (Helm chart `kong-mesh`, `controlPlane.mode: zone`, no
Global) and Universal (`kuma-cp run`, memory store, `KUMA_MODE=zone`). No license. Raw evidence:
[questions-raw.md](questions-raw.md), regenerated by `test/e2e/run.sh questions`.

## MeshCircuitBreaker with only `outlierDetection.healthyPanicThreshold`

**Rejected on 3.0, and on 2.14.** Both Kubernetes and Universal:

| `outlierDetection` | 2.14 and 3.0 |
|---|---|
| `{healthyPanicThreshold: 50}` | `detectors: must be defined` |
| `{healthyPanicThreshold: 50, detectors: {}}` | `detectors: must have at least one defined: totalFailures, gatewayFailures, localOriginFailures, successRate, failurePercentage` |
| `{healthyPanicThreshold: 50, disabled: true}` | `detectors: must be defined` |

Whether it would take effect is moot since it cannot be stored. From the 3.0 configurer
(`kuma/pkg/plugins/policies/meshcircuitbreaker/plugin/xds/configurer.go`,
`configureOutlierDetection`): with `disabled: true` the function returns before
`configureHealthyPanicThreshold`, so the threshold is only written to
`cluster.common_lb_config.healthy_panic_threshold` when outlier detection is enabled, which needs
a detector. No dataplane was run; this is read from source.

The migrator's companion (`detectors.totalFailures.consecutive: 5` plus the threshold) is
accepted by both versions. Its report text already says this turns on outlier ejection.

## Top-level `targetRef.kind: MeshGateway` on 2.14

| Policy | `kong-mesh-system` (system role) | app namespace `kuma-demo` | Universal |
|---|---|---|---|
| `MeshTimeout` | accepted | **rejected**: `spec.targetRef.kind: value 'MeshGateway' is not supported` | accepted |
| `MeshTrafficPermission` | rejected (not in its supported kinds at all) | rejected | rejected |
| `MeshAccessLog` (`from[]`) | accepted | accepted | accepted |

So on 2.14 the system-role exception exists for `MeshTimeout` (app namespace rejected, system
namespace accepted), `MeshTrafficPermission` never accepts `MeshGateway`, and `MeshAccessLog`
accepts it in any namespace. On 3.0 every top-level `targetRef.name` is an unknown field, so any
`MeshGateway` reference fails before kind validation (`spec.targetRef.name: unknown field`).

## `Mesh` fields on 3.0

| `spec` | Kubernetes 3.0 | Universal 3.0 | Stored by Universal 3.0 |
|---|---|---|---|
| `constraints: …` | accepted, no warning | accepted, no warning | dropped (`{}`) |
| `mtls: {builtin backend}` | accepted, no warning | accepted, no warning | dropped (`{}`) |
| `metrics: …` | accepted, no warning | accepted, no warning | dropped |
| `routing.defaultForbidMeshExternalServiceAccess` | accepted, no warning | accepted, no warning | dropped |
| `meshServices.mode: Everywhere` / `ReachableBackends` / `Disabled` | **rejected**: `spec.meshServices.mode: removed in 3.0 and every mesh behaves as Exclusive; remove the field or set it to Exclusive` | rejected (same) | — |
| `meshServices.mode: Exclusive` | **accepted with warning**: `meshServices was removed in 3.0 and is ignored: every mesh behaves as Exclusive. Drop the field before it is reserved again in a future release.` | same | kept |

`constraints` and `mtls` are not rejected: they are accepted silently and dropped. A 3.0 `Mesh`
carrying `mtls` gives no signal that mTLS is gone. The migrator's v3 `Mesh` output keeps
`meshServices.mode: Exclusive`, which triggers the warning above (see findings).

## MeshIdentity `provider.type: Extension` (configs from `site/content/topics/external-pki.md`)

| Extension | 2.14 k8s | 3.0 k8s | 2.14 uni | 3.0 uni |
|---|---|---|---|---|
| `vault` | accepted | accepted | accepted | accepted |
| `acmpca` | accepted | accepted | accepted | accepted |
| `certmanager` | accepted | accepted | accepted | accepted |

The config is validated per extension (probed by hand with `config: {bogusField: 1}`): `acmpca` gives
`config.arn: needs to be defined`, `vault` gives `config.connection: connection is required`, `certmanager` gives `config.issuerRef.name: needs to be defined`. An unknown `extension.name` is
accepted at admission.

After admission (Universal 2.14, meshServices Exclusive):

- `vault`: `ProviderInitializationError … failed to load Vault TLS CA cert: resource not found: type="Secret" name="vault-ca"` (expected, no secret)
- `acmpca`: `ProviderInitialized`, then `MeshTrustCreationError` from the AWS credential chain (expected)
- `certmanager` on Universal: `ProviderInitializationError: unknown extension "certmanager", registered: [acmpca vault]`. Confirms the docs: Kubernetes-only, but Universal **accepts** the resource and only fails in status.

No license was needed for any of this.

Related, found while probing: on 2.14 a `MeshIdentity` in a mesh without
`meshServices.mode: Exclusive` never initialises:
`DependenciesReady=False, reason MeshServicesDisabled: MeshIdentity requires MeshServices to be enabled on the mesh. To enable, set spec.meshServices.mode: Exclusive`.
Setting `Exclusive` makes it `Ready`. See findings for what this means for the v3 checklist order.

`kumactl delete <type> does-not-exist [--mesh default]`:

| Kind | Type the report uses | Result |
|---|---|---|
| TrafficPermission, TrafficRoute, TrafficLog, TrafficTrace, CircuitBreaker, Retry, Timeout, RateLimit, FaultInjection, VirtualOutbound, ProxyTemplate, ExternalService, ZoneIngress, OPAPolicy, MeshGateway, MeshGatewayRoute, MeshGlobalRateLimit | as in the map | valid (`there is no <Kind> with name …`) |

Also: the report's kumactl context hint `kumactl config use-context <ctx>` is not a kumactl
command in 2.14.7 or 3.0.1 (prints the `kumactl config` help). The command is
`kumactl config control-planes switch --name <ctx>`.

## 3.0: legacy kinds and dangling `backendRef`

- `kubectl apply` of `TrafficPermission` on 3.0: `resource mapping not found … no matches for kind "TrafficPermission" in version "kuma.io/v1alpha1" ensure CRDs are installed first`. The CRDs `trafficpermissions`, `proxytemplates`, `virtualoutbounds`, `externalservices`, `opapolicies`, `meshgateways`, `meshgatewayinstances`, `meshgatewayconfigs`, `meshglobalratelimits`, `zoneingresses`, `zoneegresses` are all absent from the 3.0.1 chart. Universal 3.0: `invalid resource type "TrafficPermission"` (same for every removed kind, see `_manual` rows in `v3-universal.md`).
- `MeshAccessLog` and `MeshTrace` with an OpenTelemetry `backendRef` whose labels match no `MeshOpenTelemetryBackend`: **accepted** on Kubernetes and Universal 3.0, no warning. Confirms the reason `backends/` is applied first.
- A supplied `kuma.io/origin` label that differs from the computed one: 3.0 **rejects** (`label "kuma.io/origin" is managed by the control plane: got "global", expected "zone"`); 2.14 accepts it.
